# FIT-96 Design Doc: トレーニング画像を日次サマリーのデザインに揃える

作成日: 2026-09-08 / 状態: 実装済み（検証結果は末尾）

対象Issue: [FIT-96 — トレーニングの生成画像のUIを身体組成・食事側のUIに合わせる](https://linear.app/fitness-analytics/issue/FIT-96)

トレーニングのPNGを、体組成・食事の画像と同じ紙色背景、文字の階層、罫線、余白で描画する。画像化ボタンとダイアログは既存の共通スタイルを使い続け、生成画像の描画を中心に変更する。本書では、画像の揃え方、共通化する実装、受け入れ条件を提案する。

調査上の制約: Linear連携が再認証を要求し、Web経由でも本文を取得できなかった。Issue本文・添付・コメントは未確認であり、要件の根拠はユーザーが提示したIssueタイトルと現行コードに限る。以下の具体的なレイアウトは設計提案であり、Issueで指定された仕様とは区別する。実装着手時に本文を確認し、追加要件があれば本書へ反映する。

## 現状はダイアログよりもPNGの見た目が異なる

[TrainingRecordExport](../components/training-record-export.tsx) と [DailySummaryExport](../components/daily-summary-export.tsx) は、どちらもブラウザーのCanvasでPNGを生成し、Object URLをプレビューする。ボタン、ダイアログ、共有操作は同じ `record-export-*` CSSを使っている。両者の主な差分はCanvas内にある。

| 比較軸 | トレーニング画像の現状 | 体組成・食事画像の現状 |
| --- | --- | --- |
| サイズ | 幅1080、最小高さ1350 px。セット数で高さを拡張 | 1080 × 1520 px |
| 左右余白 | 72 px | 86 px |
| 配色 | アプリのCSSトークン。青い装飾、色付きパネル | 背景 `#fbfaf7`、本文 `#24231f`、補助文字 `#77746d` |
| ヘッダー | 青い短線、日付、日本語タイトルの順 | `DAILY LOG`、日付の順 |
| 本文 | 角丸パネル内で種目別にまとめ、セットを3列のチップで表示 | セクション見出しと罫線、項目名を左、数値を右に配置 |
| フッター | KIZMと `#トレーニング記録` | 罫線、KIZMと `#fitness #食事記録` |
| ダイアログの日付 | 月日・曜日 | 年月日・曜日 |

セットは `setCount` 分だけ展開される。`MAX RM` は [getWorkoutSetsWithRecords](../lib/fitness/fitness.ts) の判定結果を使い、展開後の先頭セットにだけ表示する。日付ごとの最高推定1RMが過去最高を上回った種目が対象で、初回記録や同値は更新扱いにならない。この意味を見た目の変更で変えない。

現在のE2Eにはダッシュボードのvisual regressionがあるが、画像化ダイアログや生成PNGを直接確認するテストは見当たらない。既存のページ画像だけでは、今回の変更を検証できない。

## 紙面のルールを揃え、トレーニング固有の情報を残す

共通の外観は日次サマリーの現行値を基準にする。トレーニングのタイトルは `TRAINING LOG` とし、ダイアログと画像の代替テキストでは「トレーニング記録」を使う。青い装飾線、本文の角丸パネル、セットの色付きチップを外し、種目ごとの罫線と行間で情報を区切る。

| 要素 | 提案する仕様（生成画像内のpx） |
| --- | --- |
| 基本寸法 | 幅1080、左右余白86、本文幅908、最小高さ1520 |
| 配色 | 背景 `#fbfaf7`、本文 `#24231f`、補助文字 `#77746d`、罫線 `#d8d5ce`、フッター文字 `#aaa69e` |
| フォント | 現行と同じbodyのフォント。`document.fonts.ready` 後に計測・描画 |
| ヘッダー | タイトル700/72 px、ベースラインy=150。日付600/29 px、y=205 |
| 種目見出し | 最初の見出しはy=330、700/30 px。見出し末尾の下38 pxに高さ2 pxの罫線 |
| セット行 | 1セット1行。左にセット番号、右に重量と回数。行高90 px、数値700/52 px、ラベル・単位600/27 px |
| 記録更新 | 該当行のセット番号の下に `MAX RM` を700/24 pxで表示。薄い赤 `#f3dddd` の角丸背景（高さ32 px、左右余白10 px、角丸6 px）と本文色の文字で少し強調する |
| フッター | 最小高さ時は罫線y=1290、文字y=1360。KIZMを左、既存のハッシュタグを右に配置 |

以下は情報配置の概略であり、最終画像の縮尺を表すものではない。

```text
TRAINING LOG
2026年9月8日(火)

ベンチプレス
────────────────────────────
SET 1                  60.0 kg × 10 回
MAX RM
SET 2                  60.0 kg ×  8 回

スクワット
────────────────────────────
SET 1                  80.0 kg ×  8 回

────────────────────────────
KIZM                  #トレーニング記録
```

重量の小数・整数の表示は既存の `formatNumber` の指定を維持する。数値は右寄せにし、単位との間隔を一定にする。種目内のセット番号は1から始め、入力順とセット総数を保つ。種目の順序も現行の初出順を維持する。

### 長い記録は高さを伸ばし、文字を小さくしすぎない

3列から1行形式へ変えると、生成画像は縦に長くなる。320px幅のプレビューで各セットを読みやすくするため、この増加を受け入れる。セットの省略や複数画像への分割は行わない。

描画前にフォントを読み込み、種目名の折り返しと各行の寸法を計測する。種目名は本文幅で折り返し、長い英単語も必要なら文字単位で折り返す。見出しの追加行には42 pxずつ確保し、後続の罫線とセット行も下へ送る。後続種目は前の最終行の領域末尾から70 px空けて始める。

セット番号と `MAX RM` 用に左側180 pxを予約し、残りの領域に数値を描く。文字列が収まらない場合は重量と回数を2段に分け、行の高さを追加する。省略記号や極端な縮小で記録を隠さない。

本文の最終行について、文字の下端まで含めた座標を `contentBottom` とする。フッター罫線は `max(1290, contentBottom + 90)`、フッター文字は罫線の70 px下、画像下端は罫線の230 px下に置く。これで最小高さ1520 pxと、本文・フッター間の余白を両立させる。計測した結果を描画にも使い、別の高さ計算式を重複させない。

ブラウザーのCanvas上限を超える極端な件数は、既存の生成エラー表示と再試行導線で扱う。正常生成できる上限は環境によるため、固定値として保証しない。代表的な多件数ケースを検証し、実際の利用で上限が問題になる場合に画像分割を別途検討する。

### ダイアログでは既存の操作を維持する

トレーニング側の日付表記を日次サマリーと同じ年月日・曜日へ揃える。画像は幅100%・縦横比維持で表示し、長い画像は縦スクロールで最後まで見られるようにする。320 × 568、390 × 844の画面で、閉じる・共有する操作へ到達できることを確認する。操作領域は44 × 44 CSS px以上とする。

生成中の共有無効化、失敗時の再試行、Web Share API非対応時のダウンロード、共有キャンセル時にダウンロードしない動作を維持する。出力は幅1080 pxのPNG、ファイル名は `training-record-YYYY-MM-DD.png` を継続する。

## 共通化はCanvasの外観と描画処理に絞る

画像の色と寸法をトレーニング側へコピーするだけでは、次の修正で差分が戻りやすい。そこで、両画像が参照する小さな描画モジュールを設ける。ダイアログ全体や共有処理の汎用化は、このIssueでは行わない。

| ファイル（新規は予定） | 役割・変更内容 |
| --- | --- |
| `components/export-image/export-image-style.ts`（新規） | PNG共通の色、幅、余白、文字サイズを定義 |
| `components/export-image/export-image-canvas.ts`（新規） | 背景、ヘッダー、罫線、フッターの描画。Canvasとフォントは呼び出し側から渡す |
| `components/training-record-image/training-record-image.ts`（新規） | トレーニング固有の文字計測、折り返し、配置、PNG生成 |
| `lib/fitness/training-record/training-record.ts`（新規） | 既存の種目グループ化・セット展開を移動。入力はドメイン型、出力は順序を保った種目別セット |
| `lib/fitness/training-record/training-record.test.ts`（新規） | 展開数、順序、`MAX RM`の保持を検証 |
| `components/training-record-export.tsx` | 画像生成を新モジュールへ委譲し、UI状態と共有操作を担当。日付表記を統一 |
| `components/daily-summary-export.tsx` | 共通描画を利用。既存PNGの寸法・色・座標・内容を維持 |
| `design.md` | 書き出し画像共通の配色・文字・余白を追記 |
| `e2e/record-export.spec.ts`、`e2e/record-export.visual.spec.ts`（新規） | 両画像の操作と描画を検証 |

セット展開とグループ化は現在UIファイルにあるが、変換処理なので移動先を `lib/fitness/` 配下とする。記録更新の判定は既存の `getWorkoutSetsWithRecords` を再利用する。Canvasの座標やブラウザーAPIはドメイン層へ持ち込まない。新しいファイルは具体名を付け、`index.ts` を追加する場合は再エクスポートだけに使う。

`FitnessDataSource`、Notion adapter、データ取得範囲、最新日の選択は変更しない。`app/` の取得契約を維持し、Client ComponentへSDKや環境変数を持ち込まない。追加ライブラリも不要である。

[design.md](../design.md) はアプリ画面全体の寒色系トークンを定めている一方、現在の日次サマリーPNGは暖色系の固定色を使っている。この差を解消する方向は「日次サマリーへ揃える」という今回の依頼と異なるため、書き出し画像の共通仕様を同文書に明記する。アプリ画面のテーマはそのままとする。

## 実装は既存画像の基準を残してから置き換える

1. Issue本文の追加要件と最新の統合先との差分を確認する。Next.js関連コードを編集する前に、インストール済みの `node_modules/next/dist/docs/` でClient ComponentとImageの関連ガイドを読む。
2. 日次サマリーの生成PNGを固定Linux環境で撮影し、変更前の基準を残す。トレーニングも通常記録と記録更新の表示内容を確認する。
3. 共通描画とドメイン変換を抽出する。日次サマリーが変更前の基準と一致し、セットの内容・順序が保たれることを確認する。
4. トレーニングのレイアウトを置き換え、両画面幅で操作と画像を検証する。生成画像のbaselineを目視確認して追加する。

## 受け入れ条件は画像と操作の両方で確認する

| 対象 | 検証内容 |
| --- | --- |
| 外観 | 両PNGの背景、左右余白、タイトルと日付の配置、罫線、フッターが同じ仕様。トレーニング画像に旧パネル・チップ・装飾線が残らない |
| データの維持 | 同一種目の複数行、複数種目、`setCount > 1` で全セットを入力順に表示。重量と回数を変更しない |
| 記録更新 | 過去最高更新、同値、初回記録を確認。展開後に `MAX RM` が複製されない |
| 境界 | 1セット、3セット、4セット、長い日本語・英語の種目名、大きい数値、10種目×10セットで欠け・重なりがない |
| PNG | 通常・長文・多件数で生成成功。幅1080、最小高さ1520、必要に応じた高さ拡張、フッターまでの表示を確認 |
| モバイル | 320pxと390pxの双方で開く、生成完了、共有、閉じる、再度開く。横スクロールなし。縦スクロール後も全内容と操作に到達できる |
| 生成失敗 | `toBlob` の失敗等をブラウザーテストで再現し、エラー表示→再試行→プレビュー表示を確認 |
| 共有 | API非対応時のPNGダウンロード、API対応時のファイル共有、キャンセル時の無処理、その他の共有失敗時のダウンロードを確認 |
| 日次サマリー | 共通化の前後で既存PNGが一致し、画像化・共有操作も動く |

変換のunit testは実装と同じディレクトリに置く。折り返しは実際のフォント計測に依存するため、Canvasを使うブラウザーテストで確認する。モバイルのダイアログ撮影に加え、Blobから取得したPNG全体も比較し、スクロール領域の外にある欠けを見逃さない。共有APIはスタブで分岐と渡すファイルを検証し、OSの共有シートの表示は実機で手動確認する。

通常データは既存fixtureを使う。長文・多件数は描画モジュールにテストデータを渡すブラウザーテストで検証し、共通fixtureの内容を変更しない。テストのためだけの分岐や公開ルートを製品コードへ加えない。

実装後は `pnpm verify` に加え、次を成功させる。

```sh
pnpm exec playwright test e2e/record-export.spec.ts --project chromium-320 --project chromium-390
```

visual regressionは [テスト運用](./testing.md) の固定Linux環境で実行する。

```sh
PLAYWRIGHT_VISUAL_REGRESSION=true pnpm exec playwright test e2e/record-export.visual.spec.ts --project chromium-320 --project chromium-390
```

baselineは実装結果を目視してから採用し、更新なしで再実行する。E2Eのポート、build、reportは対象worktree内で分離する。統合前には最新の統合先へ追従し、共有描画・fixture・baselineの競合を確認して、リポジトリ規約の `pnpm verify:all` と必要なvisual regressionを再実行する。

## 判断が必要な点と採用しない案

提案の中心は、外観だけでなくセットの3列表示も1行形式へ揃える点にある。既存の3列を残す案は画像を短く保てるが、日次サマリーとの数値配置の差と小画面での読みづらさが残るため採用しない。Issue本文でコンパクトさが指定されている場合は、この判断を見直す。

タイトルの `TRAINING LOG` と暖色系配色も提案である。日本語タイトルの継続や、PNGもアプリ画面の色へ揃える意図が本文にある場合は、共通仕様を確定する前に調整する。ダイアログ・共有ロジック全体の統合、画像分割、データ集計や記録更新ルールの変更は別の課題として扱う。

## 実装結果

上記の構成で実装した。数値の表示と記録更新の意味を維持し、通常fixtureの10セットは1080 × 1835 pxのPNGになる。長い種目名は文字単位で折り返し、重量・回数が1行に収まらない場合は別の行へ送る。`MAX RM`には比較検討の結果、薄い赤 `#f3dddd` を採用した。既存のダイアログCSSで320pxと390pxの表示・スクロール・操作が成立したため、CSSの変更は不要だった。

Linuxで保存した変更前の日次サマリーPNGをbaselineに使い、共通化後も一致することを確認した。追加したvisual regressionでは、両画面幅のダイアログ、通常のPNG全体、長い種目名と大きい数値のPNG全体を検証する。ブラウザー向けのテスト用コードは `e2e/helpers/training-record-renderer.ts` で組み立て、製品にテスト専用ルートや分岐を追加していない。

Linear本文の取得は実装時にも再認証エラーとなったため、ユーザーが実装を指示した本書の提案を基準にした。OSの共有シートは実機を操作できないため未確認。自動テストでは共有ファイルの名前・形式・サイズと、成功・キャンセル・失敗時の分岐を確認する。

検証結果: `pnpm verify` の全6工程が成功（unit test 145件）。320px／390pxの操作E2Eは22件、固定Linux環境のvisual regressionは3件成功した。PNGが画面幅に依存しない長文ケースは390pxで比較し、320px側の重複ケース1件は意図的にスキップしている。追加baseline全7画像を目視確認した。ビルドでは既存のLINE Seed JPのfallback font生成に関する警告が出るが、ビルド自体は成功している。
