# FIT-97 Design Doc: 記録日を選んで画像を生成する

ステータス: 実装済み（本書の方針で実装依頼を受領。Issue本文は未取得）

作成日: 2026-09-08

対象: [FIT-97 — 日付を変えて画像生成できるようにする](https://linear.app/fitness-analytics/issue/FIT-97/日付を変えて画像生成できるようにする)

画像生成ダイアログに記録日の選択欄を追加する。日次サマリーとトレーニング記録の両方で、取得済みの記録日を選ぶと、その日の内容でPNGを再生成する。初回は従来どおり最新の記録日を表示する。

本書は実装担当者とレビュー担当者に向けた対応案である。Linear接続が再認証を要求し、Web経由でも本文を取得できなかったため、要件の根拠はIssueタイトルと現行コードに限る。「両方の画像が対象」「選べる範囲は取得済みデータ」「日付変更は記録内容の切り替えを意味する」は提案上の仮定であり、Issueの確定要件として扱わない。

## 現在は生成対象が最新日に固定されている

調査時点のcommitは `488ac90`。実装上の制約は次のとおり。

| 箇所 | 現在の動作 | 設計への影響 |
| --- | --- | --- |
| [`app/page.tsx`](../app/page.tsx) | `logs.at(-1)`を日次画像に渡し、トレーニングは最新日のセットと全履歴を渡す | 日次画像にも取得済みの履歴を渡す必要がある |
| [`DailySummaryExport`](../components/daily-summary-export.tsx) | 単一の`FitnessLog`からCanvasで生成し、完成画像を再利用する | 日付を変えたら生成結果を無効化する |
| [`TrainingRecordExport`](../components/training-record-export.tsx) | 最新日のセットから日付を求め、全履歴でMAX RMを判定する | 選択日を明示し、過去の記録判定に全履歴を使う |
| [`lib/notion.ts`](../lib/notion.ts) | Daysは今日から83日前を含む週の月曜以降を取得。Workoutsは日付フィルタなしで取得する | 日次画像で全期間を選べるわけではない |
| [`getWorkoutSetsWithRecords`](../lib/fitness/fitness.ts) | 指定日より前の記録と比較し、指定日のセットだけを返す | 過去日への切り替えでも既存の判定を再利用できる |

両画像の共有処理はWeb Share APIを使い、ファイル共有に対応しない場合はダウンロードする。PNGは幅1080pxで、日次は高さ1520px、トレーニングは内容に応じて高さが変わる。この出力形式は継続する。

## 日付は画像ごとに選ぶ

既存の画像化ボタンからダイアログを開き、見出しの下に置く「記録日」のネイティブ`select`で切り替える。選択肢は対象の画像に使える記録日だけとし、新しい順に並べる。日次とトレーニングの選択状態は独立させる。

| 操作・状態 | 期待する動作 |
| --- | --- |
| 初回に開く | 対象データの最新日を選択し、自動生成する |
| 別の日を選ぶ | 旧プレビューを外し、共有を無効にして、選択日の画像を自動生成する |
| 同じ日を選ぶ | 完成済みなら再生成しない |
| 閉じて再度開く | データが変わっていなければ選択日と完成画像を維持する |
| 生成中に閉じる | 処理が完了してもダイアログを再表示しない |
| 記録日が1日だけ | 選択欄にその日を表示する。画像生成と共有は通常どおり使える |
| 記録がない／取得に失敗した | 対象の画像化ボタンは表示しない。既存の空状態・エラー表示を使う |
| 生成に失敗した | 共有は無効のまま、選択日を保って「もう一度作る」を表示する |

未記録日を選べるカレンダーや前日・翌日ボタンは追加しない。欠けた日を避けながら選べる`select`で初期実装を小さく保つ。日次は「読み込み済みの記録日から選べます」と補足し、取得期間外の記録まで選べると誤解させない。

日次画像は選択日の1レコードを使い、欠損値は既存の「—」を維持する。別日の体重や栄養値による補完は行わない。トレーニング画像は選択日の全種目・全セットを含める。チャートで選択中の種目や日付、ダッシュボード全体の表示には連動させない。

320pxを基準に、選択欄は見出しの下で全幅を使う。閉じるボタンと選択欄・共有ボタンは44×44 CSS px以上の操作領域を確保する。長い画像はダイアログ内で縦スクロールし、日付選択や共有操作に到達できるようにする。既存のデザイントークンとフォーカス表示を使い、`label`を選択欄に関連付ける。生成状態は既存の`aria-live`と`aria-busy`で伝える。

## データ取得を増やさず、ドメイン層で生成対象を選ぶ

`FitnessDataSource`の契約とNotion adapterは変更しない。`app/page.tsx`が現在取得しているシリアライズ可能なドメインモデルをClient Componentに渡す。

| 変更箇所 | 責務 |
| --- | --- |
| `app/page.tsx` | 日次には`logs`、トレーニングには`workoutHistory`を渡す。最新日の事前抽出を画像化propsから外す |
| `lib/fitness/image-export/image-export.ts`（新規） | 記録日の重複除去・降順整列、選択日の対象取得、描画用データへの変換を純粋関数で行う |
| `lib/fitness/image-export/image-export.test.ts`（新規） | 日付選択と生成対象の境界条件を検証する |
| `components/image-export/use-image-export.ts`（新規） | 両画像で共通の生成ID、プレビュー、Object URLの寿命を管理する |
| `components/daily-summary-export.tsx` | 選択日、生成状態、日次画像の描画・共有を管理する |
| `components/training-record-export.tsx` | 選択日、生成状態、トレーニング画像の描画・共有を管理する |
| `app/globals.css` | 既存の`record-export-*`に日付選択欄のスタイルを追加する |
| `e2e/image-export.spec.ts`（新規） | 両画像の切り替えと共有、競合、モバイル操作を検証する |

日付の内部表現は既存の`YYYY-MM-DD`を維持する。候補を入力配列の順序に依存せず整列し、初期値は最大の日付とする。新たな日付判定が必要なら`lib/calendar-date`の`isCalendarDate`を再利用し、日付表示は既存どおりUTC指定で端末のタイムゾーンによるずれを防ぐ。

日次の同日レコードが複数ある場合は、入力配列の末尾にある1件を採用し、値を合算・混在させない。これは現在の最新日での`logs.at(-1)`と整合させる暫定方針である。モデルに更新日時や優先順位がないため、取得をまたいだ同日レコードの厳密な優先順位は保証できない。選択日のレコードが見つからない場合は画像を生成せず、候補から最新日を選び直す。

トレーニングのMAX RMは、`getWorkoutSetsWithRecords(workoutHistory, selectedDate)`を利用する。選択日のセットだけを渡すと過去との比較ができなくなるため、全履歴を保持する。選択日より後の記録は比較対象に含めない。同日の最高値へのマーク、初記録にはマークしない動作、`setCount`展開時の最初のセットだけへのマークを維持する。

現在UI内にあるトレーニングの種目別グループ化とセット展開も、この変更でドメイン層に移す。Canvasの座標・フォント・高さ計算は表示の責務としてコンポーネント側に残す。`index.ts`を追加する場合は再エクスポートだけにする。

## 古い画像を新しい日付で共有しない

日付だけをstateに追加すると、旧画像が`ready`のまま残ったり、非同期生成の完了順が逆転したりする。生成結果は日付と入力データに結び付けて管理する。

1. 開く・日付変更・再試行の開始時に、単調増加する生成IDを更新する。選択日と描画対象をその時点で確定する。
2. 旧プレビューを取り除いてObject URLを解放し、状態を`rendering`にする。生成中も日付選択は可能にするが、共有は無効にする。
3. 生成完了時は、その生成IDが最新かつコンポーネントが有効な場合だけ結果を採用する。古い成功・失敗はどちらも無視する。
4. 採用した結果に`date`、`filename`、`blob`、`url`、`height`をまとめて保持する。共有・ダウンロード・altはこの結果を参照し、選択日と一致した完成画像だけ共有できるようにする。
5. 画像の置き換えとアンマウントでObject URLを解放する。破棄した生成処理ではURLを作らず、作成済みなら即座に解放する。状態更新関数内でのURL解放は避け、所有箇所を一本化する。

例として、A日を生成中にB日へ変更した場合、B日の画像が完成した後にA日の処理が終わっても表示は変えない。A日の処理が失敗しても、B日の成功表示をエラーに戻さない。

「更新する」で取得データが変わった場合は、両コンポーネントをデータ内容に基づく`key`で再マウントし、選択日と画像をリセットする案を採る。現在トレーニングで使われている`JSON.stringify(workoutSets)`と同じ方式を日次にも適用する。更新結果が同一なら状態を維持し、同日でも値が変われば古い画像を破棄する。更新後はダイアログを閉じ、次回開いたときに最新日で生成する。

ファイル名は`daily-summary-YYYY-MM-DD.png`と`training-record-YYYY-MM-DD.png`を継続する。共有キャンセル時はダウンロードせず、それ以外の共有失敗時は既存のフォールバックを維持する。

## 全期間対応は取得契約の変更が必要になる

| 案 | 記録日の選びやすさ | 取得処理への影響 | 判断 |
| --- | --- | --- | --- |
| ダイアログ内で取得済み記録日を選ぶ | 記録がある日だけを選べる | 追加通信なし。既存の契約を維持 | 本書の推奨案 |
| カレンダーから任意日を選び、都度取得する | 取得期間外も選べるが未記録日への対応が必要 | 日付指定のport、adapter、取得エラー・キャッシュ設計を追加 | 全期間が必須なら再設計する |
| ページ全体の日付と画像を連動させる | 他の表示と同じ日を共有できる | 各セクションとURL状態の意味も変更 | 画像生成だけの要望には変更範囲が広い |

今回の提案は画像の日付選択に絞る。画像のレイアウト刷新、記録の日付編集、複数日の一括出力、サーバー側での画像生成は対象外とする。

## 受け入れ条件は画像内容まで確認する

実装時は`pnpm verify`を必須とする。追加するドメインロジックには隣接するunit testを付け、少なくとも以下を確認する。

- 空配列、1日、複数日、順不同、同日の重複から正しい候補と初期日を得る。
- 選択日の日次レコードだけを返し、欠損値を別日で補わない。同日の複数レコードは末尾を採用する。
- 選択日の全トレーニングを取得し、過去日のMAX RM判定が後日の高記録に影響されない。
- 種目別グループ化、セット数の展開、MAX RMマークの位置が移動前と一致する。

操作E2Eは`chromium-320`と`chromium-390`の両方で次を検証する。異なる日付・数値を持つ既存fixtureを使い、足りない場合だけシナリオを追加する。

| ケース | 確認内容 |
| --- | --- |
| 最新日から過去日へ切り替える | 両画像で見出し・alt・PNGの日付と数値・ファイル名が選択日と一致する |
| PNGを出力する | ダウンロードした実ファイルのPNG形式、幅1080px、画像種別ごとの高さを確認する |
| 日付を素早く切り替える | Canvasの非同期完了をテスト内で制御し、古い成功・失敗が新しい画像を上書きしない |
| 生成失敗から再試行する | 旧画像を共有できず、選択日を保って復旧する |
| 閉じて再度開く／生成中に閉じる | 選択日を維持し、閉じたダイアログが勝手に開かない |
| 同日の数値を更新する | データ変更後に旧画像を再利用しない |
| 空データ・部分エラー | 該当する画像化ボタンだけ非表示になり、正常側は利用できる |
| 共有APIの分岐 | ファイル共有成功、非対応時のダウンロード、キャンセル時の無操作、その他の失敗時のダウンロード |
| 狭い画面とキーボード | 横スクロール・内容の欠けがなく、日付選択・共有・閉じる操作とフォーカス移動が使える |

画像内容の確認はaltやファイル名だけで済ませない。Canvasの`fillText`をテスト内で観測して日付・数値を照合し、実PNGの出力確認と組み合わせる。見た目をbaselineに追加する場合は固定Linux環境を使い、[テスト方針](./testing.md)に従う。E2Eのサーバー、ポート、生成物は当該worktree内で分離する。

## 実装は要件の照合から始める

まずIssue本文と本書の仮定を照合する。特に、画像化の対象が両方か、取得期間外の日付も必要か、最新の数値を任意の日付で出したいという意味ではないかを確認する。本文を取得できない現時点では、本書冒頭の解釈を推奨する。

実装に入る前に、インストール済みNext.jsの`node_modules/next/dist/docs/`でServer／Client Component間のpropsのガイドを読む。ドメイン関数とunit test、両ダイアログの選択・生成状態、ページのprops配線とCSS、操作E2Eの順に変更する。最後に`pnpm verify`と320px・390pxの操作E2Eを成功させ、実行結果を報告する。
